Commercial Rate Approval Automation

How I eliminated a critical daily bottleneck by designing a rule-based engine that now auto-approves 70% of all SKU order requests — freeing executive time and accelerating the entire order-to-billing pipeline.

The Problem

When I joined D&H Sécheron, I was embedded directly into the commercial approval workflow — manually reviewing and approving order rate requests on behalf of the GM Commercial. Every order line item with a custom or negotiated rate had to be reviewed before proceeding to production and billing.

500+ SKU line items arriving daily, each needing a human decision. The GM's time was consumed by approvals that were completely predictable — same items, same margins, same patterns every day.

"If I'm approving the same line item for the fifth time this week, a machine should be doing it — not me."

Understanding the Logic Before Coding

Before writing a single line of code, I spent weeks doing the job manually. Through hands-on execution and analysis of historical approval behaviour, I found three clear tiers:

  • ~70% of requests fell within pre-defined commercial bands that had never once been rejected
  • ~20% required minor verification but followed a consistent pattern
  • Only ~10% were genuinely exceptional cases requiring human judgement

How I Built It

Technology Used
Python 3.xSeleniumSQL ServerpandasCustom Rule Engine

Step 1 — Data extraction. Python extracts pending approval requests from SQL Server: SKU code, customer, requested rate, standard rate, margin band, order context.

Step 2 — Rule evaluation. Each request passes through a custom rule engine — business conditions in Python logic. All conditions met → auto-approve. Any flag → exception queue for manual review.

Step 3 — Automated approval. Cleared requests approved through browser automation — navigating the interface, filling fields, and submitting exactly as a human would.

Step 4 — Exception handling. Anything not auto-approved lands in a structured report. The GM reviews only the ~30% where genuine judgement is needed.

Key Architecture Decision

I chose browser automation rather than a direct database write because the approval system had downstream dependencies triggered by the approval action itself. Writing directly to the database would have bypassed those triggers. Slightly more brittle, but far safer and compatible with the existing system.

Results
  • 70% of daily order line items now auto-approved (~350 out of 500+ per day)
  • GM Commercial's daily approval workload dramatically reduced
  • Orders reach production and billing faster — downstream pipeline accelerated
  • Zero disruption to the existing audit trail or compliance requirements

Inventory & Production Variance Analytics

Monthly models comparing what manufacturing should have consumed against what it actually consumed — surfacing wastage and inefficiencies before they become expensive problems.

The Problem

D&H was tracking raw material stock and finished goods output separately but had never connected the two into a structured variance model. Month-end reviews were happening without any quantitative view of material efficiency.

How I Built It

Technology Used
Python (pandas)SQL ServerExcelPower BIVariance Modeling

Expected consumption model. From the bill-of-materials for each finished product, I calculate theoretical raw material consumption based on actual finished goods output each month.

Actual consumption extraction. SQL Server queries against inventory and material movement tables extract actual consumption at the same SKU granularity.

Variance calculation. Difference between expected and actual calculated at item and product-category level. Both over-consumption and under-consumption surface for investigation.

Reporting. Monthly Excel reports for operational reviews; Power BI dashboard for rolling trend visibility.

Results
  • First quantitative view of production material efficiency at D&H
  • Monthly variance analysis now standard input into operational reviews
  • Identified raw material categories with consistent over-consumption patterns
  • Enabled early intervention before month-end cost surprises

Employee Web Portal with Secure Data Pipeline

A Flask web application giving 100+ field employees direct access to their own activity and incentive data — backed by a custom ETL pipeline bridging Azure SQL and PythonAnywhere without exposing the database.

The Problem

The analytics portal I built for management wasn't accessible to the reps themselves. Field employees had no way to check their own data without asking their manager, creating unnecessary overhead and information asymmetry.

The Architecture Challenge

The data source was an Azure-hosted SQL Server. Connecting a public-facing web app directly would have required opening ports and creating security risks. The solution: a local transformation layer — a scheduled Python process that connects to Azure SQL from a secure machine, transforms the data, and pushes it to PythonAnywhere via a whitelisted static IP.

Technology Used
FlaskPythonSQL Server (Azure)PythonAnywhereJSON (data layer)Static IP Whitelisting

Data pipeline. Python script runs on schedule — connects to Azure SQL, extracts and transforms rep-level data, serialises to structured JSON files.

Deployment. JSON files pushed to PythonAnywhere via whitelisted static IP. No live database ever exposed to the public internet.

Flask web app. Employees log in; app reads from pre-transformed JSON files to display personal data.

Why JSON as the data layer? Fast, stateless, easy to maintain. Schema changes only require updating the transformation script. Already MongoDB-compatible for a future migration path.

Results
  • 100+ field employees gained direct access to their own performance data
  • Manager-relay requests for individual data eliminated entirely
  • Secure architecture — no live database exposed to the public internet
  • Incentive transparency improved: reps could verify calculations themselves

Legacy Business Book Digitisation

Reconstructing a pharmaceutical reference book from degraded scanned pages — deskewing, watermark removal, layout standardisation — turning an unusable legacy document into a clean, print-ready resource.

The Problem

Synchem had a comprehensive pharmaceutical reference book that was invaluable when printed. The only surviving digital versions were low-quality scans with watermarks, inconsistent margins, skewed pages, and degraded image quality. No original source files existed.

How I Built It

Technology Used
PythonPillow (PIL)OpenCVPyPDF2NumPy

Page extraction. Scanned PDF split into individual page images using PyPDF2 and Pillow at consistent DPI.

Deskewing. OpenCV detects the dominant text angle on each page and rotates it back to straight.

Watermark removal. Stamped watermarks isolated using Pillow and NumPy image masking based on distinctive pixel value distribution, replaced with interpolated background colour.

Layout standardisation. Page borders detected and standardised for consistent margins. Brightness and contrast normalised across varying scan quality.

Reconstruction. Cleaned pages assembled back into a single PDF with consistent page size, resolution, and layout — ready for commercial printing.

Results
  • Unusable degraded scans transformed into a clean, print-ready PDF
  • Book successfully redistributed to the full field sales team
  • No manual page editing required — entirely pipeline-processed
  • Resource recovered in-house at fraction of professional restoration cost

The Motivation

I've long been interested in serialised web fiction and wanted to understand whether an open-source LLM could be fine-tuned for this genre, and more broadly, to gain hands-on experience with the fine-tuning stack that sits behind applied AI products.

What I Explored

Technology Used
PythonAxolotlLoRA / QLoRARunPod (GPU Cloud)Llama 2 / Mistral 7BHuggingFace

Model selection. Evaluated Llama 2 (7B and 13B) and Mistral 7B as base models — open weights, well-documented, within budget for GPU cloud experimentation.

  • Axolotl dramatically simplifies training configuration vs. raw HuggingFace Trainer
  • Gained working knowledge of the fine-tuning pipeline that directly informs AI PM thinking

What I Did

Stack Evaluated

Market research. Mapped the existing landscape — Notion, Obsidian, Monarch Money, MyHeritage — to understand what was already solved and where genuine gaps existed.

Scope analysis. Rigorous breakdown of which features were genuinely useful, which were scope creep, and what a realistic MVP looked like for a solo developer building in evenings and weekends.
